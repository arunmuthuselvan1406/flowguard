# FlowGuard: operations intelligence on Exasol

Operational data is late, scattered and messy. FlowGuard is one analytics layer on **Exasol Personal**
that explains downtime, balances spare parts, catches defects early and normalises supplier data.
All computation happens in SQL inside Exasol. A thin FastAPI layer and a single-page dashboard sit on top.

Built for the Exasol AI Challenge, Track 03: Factories, Fleets & Supply Chains. Team The Vangaurd (solo entry: Arun Muthu Selvan K). MIT licensed.

## The four modules

| Module | Question it answers | How it works (in Exasol) |
|---|---|---|
| **RootCause** | Why did the line stop? | Z-score of every sensor in the 60 minutes before each stoppage against that machine's own baseline (`core.v_rootcause_z`), joined with recent maintenance events |
| **PartsBalancer** | Are spare parts where the failures are? | Surplus = on hand − expected 14-day demand − minimum level (`core.v_parts_surplus`); the UI suggests transfers from surplus to shortage sites |
| **EarlyCatch** | Where does a defect start? | Control limits (mean ± 3σ) per measurement station (`core.v_qc_flags`), flagging the first drifting station instead of waiting for end-of-line inspection |
| **SupplierNormalizer** | Can inconsistent supplier files share one schema? | A column mapping is proposed per file, a human approves it, and normalised rows are loaded into `core.supplier_shipments` |

Late and out-of-order data is handled rather than hidden: every sensor reading stores both `event_ts` and `arrival_ts`.

## Architecture

```
synthetic data (app/seed.py) ─► Exasol Personal ─► SQL views ─► FastAPI (app/api.py) ─► dashboard (web/index.html)
                                 schemas: raw, core
```

## Requirements

- Python 3.10+
- A running **Exasol Personal** instance (host, port, user, password)

## Setup

```bash
git clone <your-repo-url> flowguard && cd flowguard
python -m venv .venv && source .venv/bin/activate      # Windows: .venv\Scripts\activate
pip install -r requirements.txt
cp .env.example .env                                   # then edit with your Exasol details
```

## Run

```bash
python -m app.seed                  # creates schemas, tables, views; loads synthetic data
uvicorn app.api:app --port 8000     # serves the API and the dashboard
```

Open http://localhost:8000. The header above the demo reads **"live from Exasol Personal"** when the API
reaches the database. If you open `web/index.html` directly as a file, it falls back to built-in simulated data.

Re-running `python -m app.seed` resets the data.

## API

| Endpoint | Purpose |
|---|---|
| `GET /api/health` | Checks the Exasol connection |
| `GET /api/rootcause` | Stoppages with sensor z-scores, related maintenance events and a plain-language explanation |
| `GET /api/parts` | Stock, demand and minimum level per part and site |
| `GET /api/earlycatch` | Control limits and per-station measurements for each batch |
| `POST /api/suppliers/load` | Inserts normalised supplier shipment rows into Exasol |

## Data

All data is **synthetic**, generated by `app/seed.py` with a fixed random seed. No employer or proprietary data is used.

## Limitations

- The supplier column mapping uses fixed rules in this prototype. An LLM can be plugged in for unknown formats.
- Z-score and 3σ control limits are deliberately simple, explainable baselines, not trained models.
